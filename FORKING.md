# FORKING.md — сопровождение форка DeepTutor (lss-tools)

Документ для следующего агента или владельца: что изменено относительно
upstream, как сливаться с upstream, что ломается при обновлении и как
проверять форк после слияния. История решений — в Brain, задача 1165
(`work/active/harnes/1165-Форк-DeepTutor-под-репетитора-ОГЭ/README.md`).

## Зачем форк

Платформа Этапа 2 ИИ-репетитора ОГЭ. От upstream (HKUDS/DeepTutor) нас
отличают две цели: русский интерфейс для девятиклассника и
вложения (картинки/аудио/заготовки) в банк вопросов практики. Решение
владельца 10.10.2026: правки держим только в своём форке, PR в upstream не
оформляем; цена слияний принимается сознательно.

## Правила, нарушать нельзя

- Свои модули и документы — в **новых** файлах, которых нет у upstream
  (`web/locales/ru/`, `deeptutor/services/practice/assets.py`, этот файл).
  Интеграция с API, SQLite и карточками требует точечных правок upstream-файлов.
  Правка `AGENTS.md`, `README.md`, `.gitignore` upstream = конфликт при каждом слиянии.
- `push` в `upstream` отключён намеренно (`DISABLED_no_push_to_upstream`).
- Каталог `.code-index/` закрыт через `.git/info/exclude`, не через
  `.gitignore` — см. факт `fact-20261010-cidx3` в Brain.
- Рабочая установка пакета в `D:\Project\deeptutor` — эталон «из коробки»,
  её не трогать; форк живёт в `D:\Project\deeptutor-fork`.
- Правки — атомарными коммитами; синхронизироваться с upstream регулярно,
  редкое слияние даёт крупный конфликт; merge, не rebase.

## Вложения практики (задача 1169)

- `initialize_practice` добавляет `notebook_entries.attachments_json` с исходным
  значением `[]`. Метаданные: `kind`, `name`, `path`, `sha256`, `mime`, `bytes`.
  Файлы лежат рядом с пользовательской БД: `practice/attachments/<sha256>/<имя>`.
- `POST /api/question-notebook/practice/questions/{id}/attachments` принимает
  один файл до 32 МБ. `GET .../attachments/{sha256}` отдаёт файл только после
  проверки видимости вопроса в текущей БД, записи в `attachments_json` и
  безопасного пути. Файлы пользователя отдаются с `Cache-Control: private`,
  `Content-Security-Policy: sandbox` и `X-Content-Type-Options: nosniff`.
- Импорт принимает ZIP до 64 МБ с одним манифестом в корне (`.xlsx`, `.csv`,
  `.tsv`, `.json`, до 5 МБ) и файлами в `assets/`. Колонка `asset` содержит
  имя файла или JSON-массив имён. До 500 вопросов; каждый файл до 32 МБ,
  суммарный распакованный объём до 128 МБ. Превью отклоняет отсутствующие
  файлы и опасные пути. Повторный импорт того же вопроса сохраняет одну запись.
- Вопрос показывает изображение, аудиоплеер и ссылку на скачивание файла под
  исходным именем. Заготовки информатики общим объёмом 14,3 ГБ в ZIP не
  загружаются; их публикация ссылками относится к задаче банка 1161.
- Windows требует `tzdata` для тестов и работы практики с часовыми поясами;
  зависимость добавлена в `pyproject.toml` и `requirements/server.txt`.

## Метаданные ОГЭ и баллы практики (задача 1172)

- Аддитивная миграция добавляет поля ОГЭ в `notebook_entries`: предмет, год,
  позицию, часть, формат ответа, максимум, режим проверки, источник, признак
  аналога и состояние проверки эталона. Обычный импорт без этих полей остаётся
  допустимым; строки с любыми полями ОГЭ проверяются целиком.
- Критерии позиции хранятся в `practice_question_criteria` отдельными строками
  с баллом, текстом, источником и областью применения. Импорт ОГЭ отклоняет
  пустые позицию или источник и неполные критерии.
- Автоматические оценки пишутся в `practice_score_events` вместе с максимумом.
  Оценка Chat сохраняется только при проверенном эталоне и наличии критериев;
  ответ Follow-up агента передаёт итог через закрытую строку-маркер. Chat
  извлекает её из результата текущего хода до сохранения переписки; сервер
  удаляет маркер из текста для ученика.
- Роли `admin` и `teacher` могут исправить балл. Журнал сохраняет и модельную,
  и итоговую оценку, автора и признак ручной правки. `student` и `user` получают
  `403`; без аутентификации действует локальная роль `admin`.
- Визуальная приёмка ученика остаётся ручным шагом владельца; новая схема и API
  не заменяют её.

## Полные попытки ОГЭ (задача 1176)

- `practice_exam_attempts` хранит статус и итог попытки; `practice_exam_items`
  хранит позицию, балл и снимок задания. Снимок не зависит от дальнейших правок
  банка. Эталон и объяснение API отдаёт только после завершения попытки.
- API под `/api/question-notebook/practice/exam/` проверяет готовность банка,
  создаёт вариант по всем позициям предмета, сохраняет ответы, завершает попытку
  и возвращает её результат. Экран доступен по `/learning/practice/exam`.
- Вариант использует только видимые карточки нужного года с подтверждённым
  эталоном, ответом, объяснением и максимальным баллом. Автоматическая проверка
  должна поддерживаться проверяющей функцией; режим `model` должен иметь
  критерии оценки. Chat выставляет балл по критериям, а экран связывает событие
  с текущей сессией проверки. Если
  хотя бы одной позиции не хватает, создание отклоняется с её номером. Неполный
  вариант не выдаётся за полный.
- Нулевые результаты при завершении попытки попадают в очередь повторения.
  Итог содержит первичную сумму; перевод в отметку ждёт шкалы задачи 1175.
  Число позиций сейчас основано на КИМ-2026 и требует сверки с финальными КИМ-2027.
- Проверка: `.venv\Scripts\python.exe -m pytest tests/api/test_practice_exam.py tests/agents/chat/test_oge_grading.py tests/api/test_practice.py`;
  фронтенд — `npm run typecheck`, `npx eslint` для экрана варианта и
  `npm run i18n:check`.

## Запуск форка (развёртывание 10.10.2026)

Форк живёт в `D:\Project\deeptutor-fork` и занимает обычные адреса
`127.0.0.1:8001` (бэкенд) и `localhost:3782` (фронт). Рабочая PyPI-установка
в `D:\Project\deeptutor` при этом не работает — её серверы остановлены, каталог
остался эталоном «из коробки».

```
# один раз: venv и editable-установка
py -3.12 -m venv D:\Project\deeptutor-fork\.venv
D:\Project\deeptutor-fork\.venv\Scripts\python.exe -m pip install -e D:\Project\deeptutor-fork

# запуск и остановка (первый старт сам собирает фронт, минуты)
D:\Project\deeptutor-fork\.venv\Scripts\deeptutor.exe start --home D:\Project\deeptutor-fork --detach --no-browser
D:\Project\deeptutor-fork\.venv\Scripts\deeptutor.exe stop --home D:\Project\deeptutor-fork
```

- После правок `web/` лаунчер сам пересобирает фронт при следующем старте
  (отпечаток исходников, каталог `web/.next-deeptutor`).
- Конфиги в `data\user\settings\` скопированы из рабочей установки
  10.10.2026, `interface.json` переписан без BOM (LF, UTF-8) и с `language: ru`.
  Файлы данных форка — UTF-8 **без** BOM: читатель настроек при сбое чтения
  молча подставляет дефолты (BOM в `interface.json` выглядит как «язык не
  применяется»).
- В `model_catalog.json` лежит литеральный ключ OpenRouter — файл локальный,
  наружу не отдавать.

## Порядок слияния с upstream

```
git fetch upstream
git merge upstream/main        # merge, не rebase
```

Ожидаемые места конфликтов (по опыту этого слияния):

- `web/locales/en/app.json` — upstream добавит ключи. Конфликта почти не
  будет (мы меняли только одну строку `language.russian`), но после слияния
  ru отстанет от en: см. «Что ломается».
- `web/scripts/i18n_audit.mjs` — правьте только блок `MIN_USED_COVERAGE`.
- `web/i18n/languages.ts` и `web/i18n/init.ts` — если upstream добавит свою
  локаль, наши строки `ru` сохраняются рядом.
- `deeptutor/services/settings/interface_settings.py`,
  `launch_settings.py`, `settings_spec.py` — держим строку `ru` по образцу
  соседних локалей.
- `deeptutor/services/practice/importing.py`, `storage.py`,
  `deeptutor/api/routers/practice.py`, `question_notebook.py`,
  `deeptutor/services/session/sqlite_store.py` и две карточки фронта —
  места интеграции вложений. После слияния проверить миграцию,
  сериализацию списка и проверку владельца при раздаче.

## Что ломается при обновлении

1. **Аудит strict.** Локаль без пола в `MIN_USED_COVERAGE` (de, zh, pl, ru)
   обязана переводить все используемые ключи. Новые en-ключи после слияния
   уронят гейт на ru с ошибкой «N t() literals lack a locale entry».
   Лечение: перевести новые ключи (список — `node scripts/i18n_audit.mjs
   --show-missing`), а не возвращать пол.
2. **Русские формы множественного числа.** В `ru/app.json` есть ключи
   `_few`/`_many`, которых нет в en — это норма (так же устроен pl).
   Не «чистить» их как мусор: без них i18next не разрешит множественное
   число по-русски.
3. **Тест `test_russian_locale.py`** требует `set(en) ⊆ set(ru)` и
   `language.russian` в каждом каталоге — тот же сигнал, что и аудит.
4. **Второй канал `{zh, en}`.** Кроме react-i18next в коде есть ad-hoc
   записи `Lang` (тип в `web/features/settings/navigation/settings-nav.ts`,
   локальные копии в `SpaceDashboard.tsx`, `ConnectedAgents.tsx`,
   `next-step-copy.ts`, `ConnectionsEditor.tsx`,
   `ToolsSettingsSection.tsx`, `SubagentSettingsEditor.tsx`) с бинарным
   выборщиком «zh ? zh : en». Теперь почти везде `Lang = { zh, en, ru }`
   с обязательным ru — новый upstream-элемент без ru не соберёт
   `npm run typecheck`, дописывайте перевод. Исключение —
   `SubagentSettingsEditor.tsx`: свой локальный тип, 93 строки, редактор
   субагентов (админский); ru там пока нет, остаётся английский.
5. **Драфт настроек.** Выбор языка в настройках ставит черновик; изменение
   применяется кнопкой «Применить изменения» (upstream-механика draft/apply,
   не дефект). Бэкенд форка нормализует `ru` и не даёт ему слетать в `en`,
   как в upstream.

## Проверка форка после слияния

```
cd web
npm ci
node scripts/i18n_audit.mjs      # все локали strict, включая ru: 100%
npm run test:node                # ~1300 тестов, включая language-preferences
cd ..
py -3.12 -m pytest tests/i18n    # пер-локальные suites, включая русский
D:\Project\deeptutor-fork\.venv\Scripts\python.exe -m pytest tests/api/test_practice.py tests/api/test_practice_assets.py tests/api/test_practice_exam.py
```

Затем руками: поднять сервер, выбрать «Русский» в настройках, пройти экраны
чата, настроек и практики — формулировки смотрит владелец.
